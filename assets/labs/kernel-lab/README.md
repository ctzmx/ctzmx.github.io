# RTX 5080 kernel lab

Companion to the Chinese tutorial “从零开始写 GPU Kernel”. These examples
teach GPU indexing, masked memory access, reductions, fusion and tiled GEMM.
They are forward-only, contiguous-tensor examples, not production operators.

## Environment

Run under Linux / WSL2 with an NVIDIA GPU. The recorded environment uses
Python 3.12, PyTorch 2.9.1+cu128 and Triton 3.5.1. The exact installed package
versions are in `requirements-lock.txt`.

```bash
sudo apt-get update
sudo apt-get install -y python3-venv python3-dev gcc libc6-dev
python3 -m venv ~/venvs/kernel-lab
source ~/venvs/kernel-lab/bin/activate
python -m pip install torch==2.9.1 --index-url https://download.pytorch.org/whl/cu128
python -m pip install numpy==2.2.6
```

Download all `.py` files in this directory into one directory. Alternatively,
clone the blog repository and `cd assets/labs/kernel-lab`.

To match all recorded package versions, also download `requirements-lock.txt`
and install it inside the activated Python 3.12 environment:

```bash
python -m pip install -r requirements-lock.txt
```

## Run

```bash
python first_add.py
python lab.py --mode check --output my-checks.json
python lab.py --mode all --output my-results.json
python lab.py --mode bench --timing events --output my-events.json
python inspect_codegen.py --output my-codegen.json
python summarize.py my-results.json
```

`--mode bench` checks every Triton candidate and the RMSNorm/GEMM baselines
against a reference. The three `torch.add(out)` cases are timing baselines;
the add reference is computed with PyTorch, without a separate self-check
of that baseline. This gives 44 numerical checks for 47 timed cases. `all`
also runs edge cases and interface rejection tests. `summarize.py` validates
the recorded Python source hashes (UTF-8 with normalized LF line endings)
and emits every benchmark row. A hash
failure means the source and report do not belong to the same revision.

## Measurement contract

- Default: nine CUDA-event samples, each measuring a CUDA Graph with 64
  consecutive operations, divided by 64. Warmup: 30 calls on a side stream,
  plus five graph replays. Compilation and capture are outside timing.
- `--timing events`: the same operation loop submitted by Python without
  graph replay. The interval can include GPU starvation due to host dispatch.
- All inputs stay on the GPU; the same buffers repeat without cache flush.
  Add and GEMM use preallocated outputs for both Triton and PyTorch. RMSNorm
  returns a new tensor; graph replay uses captured allocation addresses.
- FP32 add; FP16 RMSNorm performance cases; FP16 GEMM inputs/output with FP32
  accumulator. RMSNorm correctness additionally covers BF16 and FP32.
- Every RMSNorm baseline explicitly uses `eps=1e-6`. FP64 references and
  per-case absolute/relative tolerances are recorded. FP16 intermediate
  rounding can differ in the native PyTorch implementation.
- GEMM shapes are `[M,N,K]` in JSON, whereas input A is `[M,K]` and B `[K,N]`.
  PyTorch TF32 and reduced-precision FP16/BF16 reductions are disabled.
- Effective add bandwidth uses logical `12*N` bytes; GEMM throughput uses
  the conventional `2*M*N*K` operation count. Neither measures physical
  DRAM traffic or complete-model performance.
- These are samples from a desktop GPU under WSL. Clocks are not locked;
  other applications, thermals and caches can affect results. Min/max are
  observed ranges, not confidence intervals.

`inspect_codegen.py` inspects PTX via Triton's version-specific compiled
kernel object, not final SASS. It does not replace a profiler or sanitizer.
No backward pass, arbitrary-stride support, NaN/Inf input contract or
production integration is claimed. Correctness cases are finite samples,
not a proof of all possible inputs or absence of all memory races.
Each input/output tensor is limited to at most `2**31 - 1` elements, because
these teaching kernels use 32-bit element indices. The wrappers reject larger
tensors before launching a kernel or allocating an RMSNorm output.
The GEMM uses a two-dimensional launch grid and also requires
`ceil(N / block_n) <= 65535`, the CUDA grid's y-dimension limit. Its wrapper
rejects larger column-block counts before launch.

## Recorded results

`results/rtx5080-graph.json` is the article's primary run: 303 checks passed
(259 correctness/interface cases plus 44 timed-candidate numerical checks).
Each benchmark run contains 47 shape/implementation combinations.
`rtx5080-graph-repeat.json` retains a second complete graph run because
small workloads showed substantial variation. `rtx5080-events.json` records
the ordinary Python submission path. Both additional runs passed their
44 numerical checks. The adjacent `*-tables.md` files were generated by
`summarize.py`; the article does not select each configuration's faster run.

`rtx5080-codegen.json` records one compiled 128-cubed GEMM configuration.
The codegen result is not a hardware-counter profile. No Compute Sanitizer,
Nsight, backward-pass or full-model benchmark was performed for this article.
