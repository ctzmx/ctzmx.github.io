# 博客文章模板与发布约定

适用于 `ctzmx.github.io` 的文章与站点维护。保留以下文章模板，并按文末约定验证、提交和发布改动。是否提交、推送及安装环境，遵循当前任务中用户已有的授权；使用本 skill 本身不新增操作授权。

## 文件与元信息

- 文章放在仓库的 `_posts/`，保存为 UTF-8 Markdown。
- 新文章命名为 `YYYY-MM-DD-english-slug.md`，slug 使用小写英文和短横线。
- 文件名日期、`date` 的日期部分和 `permalink` 的年月日保持一致。时间使用站点时区 `Asia/Shanghai`（`+0800`），按实际发布时间填写，不照抄范例日期。
- 使用下面的 front matter 字段顺序。`layout: post`、`author: ctzmx`、`catalog: true` 由 `_config.yml` 的文章默认值提供，背景图继承站点配置；只有需要覆盖时才在文章中声明这些字段。
- `title` 表达文章主题，`subtitle` 用一句话补充范围、价值或核心判断，不重复标题。标题和副标题使用 YAML 双引号；内容中的双引号和反斜杠需转义。
- 标签使用 YAML 列表，优先复用现有文章的标签与大小写，仅添加与内容相关的标签。
- 已发布文章仅整理格式时，保留原有发布日期、作者和永久链接，避免改变历史信息或破坏链接。

## 正文排版约定

- 文章标题由布局从 `title` 输出，正文从导语开始，不再重复一级标题。章节使用 `##`，子章节使用 `###`，不跳级。讲解 Markdown 标题语法时，可保留必要的示例标题。
- 正文章节较多或存在步骤顺序时使用 `## 1. …`、`## 2. …`；短文可以不编号，同篇保持一致。小结与参考资料可以不编号。
- 开头先说明问题和关键判断；教程可以用学习目标开场，评估与排查类文章优先给出结论。章节名称服务于实际主题，不要求每篇都套用示意标题。
- 段落、标题、列表、表格、代码块之间留空行。并列要点使用 `-`，有先后关系的步骤使用有序列表，比较信息适合用 Markdown 表格。
- 命令、路径、参数、文件名和标识符使用行内代码。围栏代码块标注语言，如 `bash`、`powershell`、`python`、`cpp`、`yaml`；目录树、日志或纯文本示意使用 `text`。
- 链接使用 `[名称](URL)`。图片使用 `![说明](/img/...)`，引用仓库内实际资源，路径中的空格写成 `%20`。
- `catalog: true` 配合站点布局自动收集二、三级标题，不另写手工目录。
- 参考资料按需提供，仅列实际使用的来源；没有引用时删除该节。区分已验证结果、推断和未验证内容。

## 修改与本地验证

- 修改前查看 `git status` 和相关历史，区分当前任务与已有的未提交改动。实现后再 review 最终 diff，确认修改范围、遗漏的调用处，以及模板与 skill 是否一致。
- 模板、样式、脚本、配置或依赖等工程修改，必须先通过本地验证再 push。使用 Ruby 3.3、仓库的 `Gemfile` 和锁文件运行实际 Jekyll 构建；缺少环境时，在已有授权范围内补齐。无法验证时明确说明阻塞，不能把静态阅读当作验证通过。

```bash
bundle install
bundle exec jekyll build --strict_front_matter --trace
bundle exec ruby scripts/check_site.rb
```

- 验证与影响范围匹配：页面布局、CSS 和浏览器脚本修改，还需在本机浏览器检查桌面与手机尺寸、资源加载和受影响交互；目录修改覆盖开启、关闭和短文章等实际分支。修复后重跑受影响的检查。
- 文章新增或元信息修改，检查构建、生成页面、资源和链接；只有拼写、说明或 skill 文档修改时，检查差异、链接和文档结构即可，skill 另跑 `skill-creator` 提供的校验器，无需机械重跑整站浏览器检查。
- 重构已有文章或发布链路时，对比改动前后的文章 URL、发布日期、作者及 RSS 链接和顺序，保留非本次任务要改变的内容。能复现的故障应验证修复前后行为，避免仅检查实现写法。
- 新增或更新依赖时提交锁文件，考虑本机 Windows 与 CI Linux 的兼容性。临时用例、截图、安装包与 `_site` 等构建产物不入库；验证结束后关闭本次启动的临时预览服务。

## Commit 与 push

- 按独立目的拆 commit，例如回退、工程重构、图片优化和 skill 更新分别提交；同一功能所需的配置、资源及调用处放在一起，保持每个提交自洽。不是按文件机械拆分，也不要求每个 commit 单独 push；可以验证后一次推送多个提交。
- Commit message 说明具体改动；需要时补充原因和验证结果，避免 `init`、`update` 等无法辨识目的的描述。暂存明确属于当前任务的文件，提交前检查 `git diff --cached` 和 `git diff --cached --check`。
- Push 前确认待推送提交和工作区状态，并获取远程最新状态，避免覆盖他人提交。通常用新提交回退已发布的改动；只有用户明确要求改写已推送历史时才这样做，并使用绑定预期远程提交的 `--force-with-lease`，发现远程变化则重新核对。
- 已获用户授权直接 push 时，完成验证后执行，不重复索要确认。没有推送授权时不因本 skill 自动推送。
- Push 成功后，核对本次提交 SHA 对应的 GitHub Actions 检查与 Pages 部署。远程失败时检查原因，在当前任务范围内修复并重新验证；外部原因阻塞时如实说明。不能用旧提交的成功结果代替本次结果，也不能把“已推送”表述成“已部署成功”。
- 完成时简要报告改动、提交、实际验证与远程结果；未完成或未验证的部分明确标出。仓库内此文件作为该项目规范的维护来源；若本机保留同源的个人副本，同步本次更新，避免两份规范分叉。
